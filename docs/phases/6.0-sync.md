# Phase 6.0 — Sync

> Release 6.0 of Hypernext (codename: Sync).
> Prerequisites: 1.0-5.0 shipped.
> Estimated duration: 8 weeks (single maintainer, AI-assisted)
> TDD requirement: Yes — same three layers.

---

## 1. Goal

Add encrypted instance-to-instance sync over WebRTC. Users with multiple Hypernext installs (e.g. desktop + laptop) can pair them via an 8-20 character pairing code and sync: bookmarks, history, settings, contacts, chat accounts, feed subscriptions.

When 6.0 ships, Hypernext users can:

- Pair two instances via a short pairing code (ECDH P-256 key exchange)
- Sync bookmarks, history, settings, contacts across paired instances
- See sync state in the Privacy Panel (or a new Sync Panel)
- Resume sync after network interruption
- Resolve conflicts manually when both instances edited the same record

This release **does not** sync chat messages, mail, or news articles (those have their own server-side history; syncing them locally is redundant). It syncs the local app state.

## 3. Sub-tasks

### 3.1 ECDH pairing (Week 1-2)

**References to consult:**

- `p256` crate (v0.14.0): <https://docs.rs/p256/latest/p256/> — ECDH on P-256 curve
- `aes-gcm` crate (v0.11.0): <https://docs.rs/aes-gcm/latest/aes_gcm/>
- `sha2` crate: <https://docs.rs/sha2/latest/sha2/>
- `hkdf` crate: <https://docs.rs/hkdf/latest/hkdf/>
- ECDH P-256 spec: NIST SP 800-186
- Original Bean's `internal/sync/crypto.go` (consult upstream — ECDH P-256 pairing was already implemented)

**Implementation:**

- [ ] Add to `crates/hypernext-sync/Cargo.toml`:

  ```toml
  p256 = { version = "0.14", features = ["ecdh", "pem"] }
  aes-gcm = "0.11"
  sha2 = "0.11"
  hkdf = "0.13"
  base32 = "0.5"  # for pairing code encoding
  flate2 = "1.1"  # for compression
  crc32fast = "1.4"  # for checksum
  ```

- [ ] `pub struct PairingCode { code: String, ecdh_private_key: p256::SecretKey }`
- [ ] Pairing code format:
  - Generate ECDH P-256 private key
  - Encode public key bytes (~65 bytes uncompressed)
  - Compress with `flate2` (deflate)
  - Encode as base32 (uppercase, no padding)
  - Add CRC32 checksum (4 bytes, base32-encoded)
  - Total: 8-20 character human-readable code (depends on compression ratio)
- [ ] Pairing flow:
  1. Instance A generates pairing code, displays to user
  2. User types code into instance B
  3. Both derive shared ECDH secret
  4. Derive AES-256 key via HKDF-SHA256 (info = "hypernext-sync-v1")
  5. Both store each other's public key + shared key
  6. Store in keychain as `sync.keypair.<peer_id>` and `sync.peer.<peer_id>.shared_key`
- [ ] **No third-party server.** Pairing is purely peer-to-peer via displayed code.

**TDD gate:**

Unit tests:

- Pairing code generation: produces valid base32 + CRC32
- Pairing code round-trip: instance A and B both derive same shared key
- CRC32 detects typo: single-char change → CRC32 mismatch
- ECDH: shared secret matches expected test vector

### 3.2 WebRTC DataChannel transport (Week 3-4)

**References to consult:**

- `webrtc` crate (v0.20.2): <https://docs.rs/webrtc/latest/webrtc/>
- WebRTC spec: <https://www.w3.org/TR/webrtc/>
- Original Bean's `internal/sync/webrtc_transport.go` (consult upstream — proposal-only)
- Phase 2.0 §3.5 WebRTC chat (consult for signaling patterns)

**Implementation:**

- [ ] `pub struct SyncTransport { peer_connection: webrtc::peer_connection::RTCPeerConnection, data_channel: webrtc::data_channel::RTCDataChannel }`
- [ ] Signaling: reuse Phase 2.0 §3.5's three signaling transports:
  - Manual SDP (default; works without any infrastructure)
  - Rendezvous HTTP endpoint (user-configured)
  - IRC PRIVMSG (requires IRC connection from 2.0)
- [ ] DataChannel: ordered, reliable (similar to TCP)
- [ ] Message framing:
  - Each frame: 4-byte length prefix + 12-byte nonce + ciphertext + 16-byte GCM tag
  - AES-256-GCM with HKDF-derived key
  - Nonces monotonic per direction (counter, never reuse)
- [ ] Heartbeat: every 30 seconds, both sides send `Ping`; expect `Pong` within 10 seconds
- [ ] Reconnect: if DataChannel drops, attempt reconnect via same signaling (with new SDP exchange)
- [ ] **Zero default ICE servers** (no STUN/TURN); user-configured for NAT traversal

**TDD gate:**

Unit tests:

- Two `SyncTransport` instances, manual SDP → connected in <5 seconds
- Send 1KB message → received on other side, decrypted
- Send 1MB message → chunked correctly
- Heartbeat: 30 seconds elapse → Ping/Pong exchanged
- Nonce monotonicity: 100 messages, nonces 1..100
- Reconnect: kill connection, restart, both reconnect via signaling

Integration tests:

- Two Hypernext instances via manual SDP, exchange 1000 messages

### 3.3 Sync domain protocol (Week 4-5)

**References to consult:**

- `yrs` crate (v0.27.3 — Yjs CRDT for Rust): <https://docs.rs/yrs/latest/yrs/>
- `automerge` crate (v0.11.0 — alternative CRDT): <https://docs.rs/automerge/latest/automerge/>
- Yjs: <https://github.com/yjs/yjs>
- Automerge: <https://automerge.org/>
- Original Bean's `internal/sync/protocol.go` (consult upstream)

**Implementation:**

- [ ] Add `yrs = "0.27"` to `hypernext-sync`
- [ ] `pub trait SyncDomain: Send + Sync`

  ```rust
  pub trait SyncDomain {
      fn name(&self) -> &'static str;  // "bookmarks", "history", etc.
      fn doc(&self) -> &yrs::Doc;       // Yjs document for this domain
      fn apply_local_change(&self, change: LocalChange) -> Result<Vec<u8>, Error>;  // returns update bytes
      fn apply_remote_update(&self, update: &[u8]) -> Result<(), Error>;
      fn snapshot(&self) -> Vec<u8>;  // serialized state for new peer
  }
  ```

- [ ] Sync domains (in priority order for v1):
  1. `bookmarks` — Yjs array of bookmark records
  2. `history` — Yjs array (with trim; keep last 10,000)
  3. `settings` — Yjs map (key → value)
  4. `contacts` — Yjs array of contact records
  5. `feed_subscriptions` — Yjs array
- [ ] **Secrets never sync.** Keychain entries stay local. Document this invariant in code.
- [ ] Message types:
  - `SyncHello(domains: Vec<String>)` — initial handshake
  - `SyncRequestSnapshot(domain: String)` — request full state for a domain
  - `SyncSnapshot(domain: String, bytes: Vec<u8>)` — full state response
  - `SyncUpdate(domain: String, bytes: Vec<u8>)` — incremental update
  - `SyncAck(domain: String, version: u64)` — acknowledgment

**TDD gate:**

Unit tests:

- Local change: add bookmark → produces update bytes
- Apply remote update: instance B receives, bookmark appears
- Snapshot: instance C joins, receives full state, all bookmarks present
- Two instances add bookmarks concurrently → both updates applied, both bookmarks present
- Concurrent edit of same bookmark field → CRDT merge resolves (last-writer-wins via vector clock)

### 3.5 Sync engine + scheduling (Week 6-7)

**References to consult:**

- Original Bean's `internal/sync/manager.go` (consult upstream)

**Implementation:**

- [ ] `pub struct SyncManager { transports: Vec<SyncTransport>, domains: Vec<Box<dyn SyncDomain>>, ... }`
- [ ] Background sync loop:
  - Listen for local changes (via `tokio::sync::mpsc`)
  - Send `SyncUpdate` to all connected peers
  - Receive `SyncUpdate` from peers, apply
  - Heartbeat every 30 seconds
- [ ] Initial sync on connect: request snapshot for each domain
- [ ] Bandwidth budget: max 1MB/min of sync traffic (configurable); throttle if exceeded
- [ ] Offline mode: changes queued in `sync_outbox` table; flushed when connection re-established
- [ ] **Pause sync in incognito:** incognito windows never sync (matching Phase 4 §3.10)

**TDD gate:**

Unit tests:

- Bandwidth budget: 2MB of changes in 1 minute → second MB queued, sent next minute
- Offline mode: kill transport, add 5 bookmarks, restore transport → all 5 sent
- Incognito: incognito window → sync manager doesn't accept changes from it

## 5. Risk register

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Pairing code is too long for users to type reliably | Medium | Low | Compress with flate2; target <20 chars; copy-to-clipboard button |
| R2 | WebRTC NAT traversal requires STUN/TURN user doesn't have | High | Medium | Manual SDP works without STUN for LAN; document limitation; recommend STUN/TURN for remote sync |
| R3 | Yjs CRDT has overhead for large datasets (10,000 bookmarks) | Medium | Medium | Trim history to 10,000; lazy-load older items from server-side (out of scope for 6.0) |
| R4 | Sync conflicts confuse users | Medium | Medium | Sensible defaults (LWW); manual resolution is opt-in |
| R5 | Incognito sync leaks data | Low | High | Enforced at `SyncManager::apply_local_change` — checks `incognito` flag on the source |
| R6 | Bandwidth budget too restrictive for power users | Low | Low | User-configurable; default 1MB/min is conservative |
| R7 | Sync transport dies mid-update; partial state | Medium | Medium | Atomic apply: Yjs updates are atomic; partial bytes rejected |

## 7. AI-agent instructions for Phase 6.0

**Before writing code:**

1. Read every URL in §6 for the layer you're working on.
2. Read `docs/references/library-lookup-protocol.md`.
3. Read `docs/references/0007-keychain-only-secrets.md` — shared ECDH keys go in keychain.
4. Read Phase 2.0 §3.5 (WebRTC chat) — signaling patterns are reused here.

**While writing code:**

1. **Secrets never sync.** Keychain entries are local-only; document this in code.
2. **Incognito never syncs.** Enforced at the SyncManager, not the UI.
3. **Pairing code is human-typable.** Test with real humans typing it.
4. **Bandwidth budget is enforced.** Don't sync 100MB of changes instantly; queue and throttle.
5. **Yjs updates are atomic.** If apply fails, the local doc is unchanged; never partial.

**After writing code:**

1. Run `cargo test -p hypernext-sync`.
2. Update `worklog.md`.
3. Conventional Commits: `feat(6.0): add ECDH pairing`, `test(6.0): cover CRDT merge`.

## 8. After 6.0 ships

Hypernext 6.0 is the **end of the original roadmap**. After 6.0:

1. **Maintain patches:** 6.0.1, 6.0.2 etc. for bug fixes; no new features in patch releases
2. **Plan 6.1 / 7.0:** based on user feedback, decide the next dimension. Candidates:
   - 7.0 Capture: research index, personal wiki, archiving (originally deferred per Wails version's `research-index-wiki-plan.md`)
   - 7.0 Media: media player (video/audio podcast feeds)
   - 7.0 Mobile: iOS/Android port (significant effort; may require UI framework switch)
   - 7.0 Collaboration: real-time collaborative editing (Hypernext instances editing shared documents)
3. **Continue hardening:** security audits, performance work, accessibility improvements
4. **Community:** publish contributing guide, accept external PRs

The dimension roadmap was designed to be extensible — new dimensions can be added without rearchitecting. The Hypernext codebase at 6.0 is the foundation for everything that comes next.
