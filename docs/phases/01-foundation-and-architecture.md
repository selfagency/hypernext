# Phase 1 — Foundation & Architecture

> Phase 1 of the Hypernext 1.0 Hypertext release.
> Prerequisites: None. This is the first phase.
> Estimated duration: 4 weeks (single maintainer, AI-assisted)
> TDD requirement: Yes — every layer below ships with tests.

---

## 1. Goal

Stand up the cargo workspace, the Relm4 + GTK4 app shell, the SQLite store with migrations, the OS keychain integration, the error/log/types infrastructure, and the CI pipeline. **No protocol code is written in this phase.** When Phase 1 ships, we have an empty app that opens a window, runs migrations on first launch, and has a passing CI gate.

The single most important outcome of this phase: every later phase can be written without touching infrastructure. If Phase 1 is wrong, every later phase pays the cost.

## 2. Sub-tasks

### 2.1 Cargo workspace skeleton (Week 1)

Hypernext is a cargo workspace with multiple crates. The layout:

```
hypernext/
├── Cargo.toml                          # workspace root
├── crates/
│   ├── hypernext-app/                  # binary crate — the app entry point
│   ├── hypernext-ui/                   # Relm4 components, GTK widgets
│   ├── hypernext-core/                 # shared types: PageDoc, Block, Metadata, errors
│   ├── hypernext-store/                # SQLite, migrations, FTS5, sqlite-vec
│   ├── hypernext-keychain/             # OS keyring wrapper
│   ├── hypernext-http/                 # HTTP client + SSRF policy + DoH (later)
│   ├── hypernext-protocol/             # Protocol trait + dispatcher (Phase 2)
│   ├── hypernext-pgp/                 # PGP verification (Phase 2)
│   ├── hypernext-webmode/              # Raw-mode webview widget wrapper (Phase 3)
│   ├── hypernext-indieauth/            # IndieAuth client (Phase 4)
│   └── hypernext-testutil/             # shared test fixtures, mock servers
├── crates-vendored/                    # fork-vendored smolnet protocol crates (Phase 2)
├── e2e/                                # Playwright E2E tests (separate package)
├── docs/                               # this plan
├── scripts/                            # CI/release helper scripts
└── .github/workflows/                  # GitHub Actions
```

    pub blocks: Vec<Block>,

### 2.6 Error types (Week 3)

**References to consult:**

- thiserror: https://docs.rs/thiserror/latest/thiserror/
- anyhow: https://docs.rs/anyhow/latest/anyhow/ — read "When to use anyhow vs thiserror"
- The original Bean's `internal/errors/errors.go` (consult the upstream repo)

**Pattern:**

- `hypernext-core/src/error.rs` defines a single top-level `HypernextError` enum with `#[derive(thiserror::Error)]`. Each variant maps to a category: `Protocol(...)`, `Storage(...)`, `Keychain(...)`, `Network(...)`, `Pgp(...)`, `Cancelled`, `InvalidUrl(...)`, `SizeLimitExceeded`, `SsrfBlocked(...)`, `Unauthorized(...)`.
- Each crate defines its own internal error type with `thiserror`, then implements `From<TheirError> for HypernextError` so errors propagate cleanly.
- The app binary uses `anyhow::Result` for top-level main and CLI commands, never for library APIs.
- Every error has a stable string code (e.g. `STORAGE_MIGRATION_FAILED`, `PGP_KEY_CHANGED`) for E2E test assertions.

**TDD gate:**

Unit tests:
- Every error variant round-trips through `Display` + `FromStr` (or `Debug` parse)
- Error codes are stable (test asserts the exact string)
- `?` operator propagates from `rusqlite::Error` → `HypernextError::Storage(...)` without manual `map_err`

## 6. AI-agent instructions for Phase 1

**Before writing any code in Phase 1, you must:**

1. Read every URL in §5.1 (Must read). Do not skip. If a URL fails to load, report it in `worklog.md` and try a different fetch method (curl, web-reader skill, etc.).
2. Read all ADRs in `docs/references/` (0001-0010).
3. Read `docs/references/crate-audit.md` to confirm crate health.
4. Read `docs/references/library-lookup-protocol.md` for the protocol on how to verify a crate before depending on it.

**While writing code:**

1. Every time you add a `use` statement for an external crate, double-check the API against the docs.rs page for the pinned version. Versions drift.
2. If a crate's API doesn't match what the phase doc describes, STOP. Update the phase doc with the actual API. Commit the doc change separately with message `docs(phase-1): correct crate API for <crate>`.
3. Write the test FIRST. The implementation follows. If you find yourself writing implementation before tests, you're doing TDD wrong — back up.
4. Use `rstest` for parametric tests wherever a function has multiple input shapes.
5. Use `pretty_assertions` for assertions on complex structs.

**After writing code:**

1. Run `cargo fmt`, `cargo clippy --workspace -- -D warnings`, `cargo test --workspace`.
2. All three must be clean before committing.
3. Append to `worklog.md` with the Task ID, your agent name, what you did, and any decisions you made.
4. Use Conventional Commits: `feat(phase-1): add SQLite migration V0001`, `test(phase-1): cover migration round-trip`, `docs(phase-1): correct rusqlite feature flags`.

**If you're stuck:**

1. Don't guess. Look up the API.
2. If the API is unclear from docs.rs, check the crate's repository README and recent issues.
3. If still unclear, document the question in `worklog.md` under a `## Open questions` section and move on. Do not block.
