# Phase 4.0 — Correspondence

> Release 4.0 of Hypernext (codename: Correspondence).
> Prerequisites: 1.0-3.0 shipped.
> Estimated duration: 12 weeks (single maintainer, AI-assisted)
> TDD requirement: Yes — same three layers.

---

## 1. Goal

Add email (IMAP/SMTP with PGP via GnuPG) and Usenet (NNTP with binary downloads via NZB/yEnc/PAR2). Hypernext becomes a "slow messaging" client alongside the real-time chat (2.0) and feed reading (1.1).

When 4.0 ships, Hypernext users can:
- Connect to multiple IMAP accounts, browse folders, read mail, send via SMTP
- Sign and encrypt emails with PGP via system GnuPG (no in-process private keys)
- Filter spam with a local Naive Bayes classifier (HMAC-token counters)
- Connect to NNTP servers, browse groups, read threads
- Download binary attachments via NZB files with yEnc decoding and PAR2 verification

### 3.4 PGP via GnuPG subprocess (Week 5)

**References to consult:**

- GnuPG Manual: https://www.gnupg.org/gph/en/manual.html
- GnuPG invocation: https://www.gnupg.org/documentation/manuals/gnupg/Invoking-GPG.html
- OpenPGP (RFC 4880): https://www.rfc-editor.org/rfc/rfc4880
- Original Bean's `internal/mail/crypto/` (consult upstream — used system GnuPG)

**Implementation:**

- [ ] `pub struct GpgClient { binary: PathBuf, homedir: PathBuf }`
  - Binary: default `gpg` from PATH; user can override in settings
  - Homedir: default `~/.gnupg`; per-account override possible
- [ ] Operations (all via subprocess):
  - `async fn verify(message: &[u8]) -> Result<VerificationResult, Error>` — `gpg --verify`
  - `async fn decrypt(message: &[u8]) -> Result<Vec<u8>, Error>` — `gpg --decrypt`
  - `async fn encrypt(plaintext: &[u8], recipients: &[String]) -> Result<Vec<u8>, Error>` — `gpg --encrypt --recipient <key>`
  - `async fn sign(plaintext: &[u8]) -> Result<Vec<u8>, Error>` — `gpg --clearsign`
  - `async fn list_keys() -> Vec<KeyInfo>` — `gpg --list-keys --with-colons`
  - `async fn import_key(key: &[u8]) -> Result<(), Error>` — `gpg --import`
- [ ] **No private keys in process memory.** GnuPG manages private keys; we never load them into Rust. We pass plaintext to GnuPG via stdin; GnuPG asks for passphrase via pinentry (separate process).
- [ ] PGP/MIME (RFC 3156): multipart/encrypted and multipart/signed handling
- [ ] Key lookup: HKP (Hochschul Key Protocol) via `keys.openpgp.org` HTTP API

**TDD gate:**

Unit tests:
- Verify valid clearsign → `VerificationResult::Valid`
- Verify tampered clearsign → `VerificationResult::Invalid`
- Decrypt: GnuPG returns plaintext
- Encrypt: GnuPG returns ciphertext
- List keys: returns 2 keys from `GNUPGHOME` test fixture
- Key import: import test key → appears in list_keys
- PGP/MIME: multipart/encrypted parsed, body decrypted

Integration tests:
- Generate test GnuPG keyring (use `gpg --batch`), full sign → verify → encrypt → decrypt flow

### 3.5 Spam classifier (Naive Bayes) (Week 6)

**References to consult:**

- Naive Bayes spam filtering: https://en.wikipedia.org/wiki/Naive_Bayes_spam_filtering
- Original Bean's `docs/plans/email-plan.md` (consult upstream — had planned Bayes implementation)

**Implementation:**

- [ ] Hand-rolled Naive Bayes (no external crate needed; ~200 LOC)
- [ ] `pub struct SpamClassifier { ham_counts: HashMap<String, u32>, spam_counts: HashMap<String, u32>, ... }`
- [ ] Tokenization: lowercase, split on non-alphanumeric, drop stopwords, drop tokens <3 chars
- [ ] Training: `train_ham(text)`, `train_spam(text)` — updates token counts
- [ ] Classification: `classify(text) -> SpamScore { probability, ham_count, spam_count }`
- [ **HMAC-token counters:** to prevent training poisoning, every training operation requires an HMAC token (per-user secret in keychain as `mail.spam.hmac_key`)
- [ ] Persistence: token counts in `spam_tokens` table (ham_count, spam_count columns)
- [ **Auto-train:** messages marked as spam by user → train spam; messages moved out of spam → train ham
- [ ] UI: spam score displayed in message list (red dot if >90% spam)

**TDD gate:**

Unit tests:
- Train 100 ham messages, 100 spam messages
- Classify a hammy message → <30% spam probability
- Classify a spammy message → >80% spam probability
- HMAC: train without valid token → rejected
- Auto-train: mark message as spam → token counts updated

- yEnc: https://www.yenc.org/
- PAR2 spec: https://en.wikipedia.org/wiki/Parchive
- Original Bean's `docs/plans/usenet-plan.md` (consult upstream)

**Implementation:**

- [ ] Add `nzb-rs = "0.6"` and `yenc = "0.2"` to `hypernext-correspondence`
- [ ] `pub struct NzbDownloader { nntp: NntpAccount, ... }`
- [ ] NZB parsing: parse XML, extract segments (each segment is a message ID)
- [ ] Download pipeline:
  1. Parse NZB → list of files, each with segments
  2. For each segment: `fetch_body(message_id)` from NNTP
  3. yEnc decode each segment
  4. Concatenate segments into final file
  5. PAR2 verify (if .par2 files in NZB)
  6. If verify fails: use PAR2 to repair (hand-rolled Reed-Solomon — or use `reed-solomon-erasure` crate)
- [ ] Progress: per-file and per-segment progress bars
- [ ] Multi-connection: parallel downloads using up to 8 NNTP connections
- [ ] Cancellation: per-file and per-batch
- [ ] Output: files saved to user-configured directory (default `~/Downloads/Usenet/`)

**TDD gate:**

Unit tests:
- NZB parsing: fixture file → 1 file with 10 segments
- yEnc decode: single segment → original bytes
- Concatenation: 10 segments → final file matches expected
- PAR2 verify: matching files → PASS
- PAR2 verify: missing segment → FAIL, repair succeeds
- Progress: 50% downloaded → 5 of 10 segments done

## 5. Risk register

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | `async-imap` API doesn't expose IDLE cleanly | Medium | Medium | Spike in week 1; if blocked, fall back to polling every 60s |
| R2 | GnuPG subprocess invocation is fragile across platforms | High | Medium | Test on macOS primarily; document Linux/Windows quirks |
| R3 | Naive Bayes accuracy is poor for first-time users | High | Low | Bootstrap with a public spam corpus (SpamAssassin public corpus) |
| R4 | NZB/yEnc/PAR2 has many edge cases (split articles, password-protected RARs) | High | Medium | Ship v1 with basic flow; document edge cases as 4.1 follow-ons |
| R5 | `nntp-rs` is fresh (399 downloads) | Medium | Medium | Hardening via tests; contribute fixes upstream |
| R6 | Multi-account mail UI complexity (account switcher, per-account folders) | Medium | Medium | Reuse Phase 4 patterns; one account per sidebar entry |

## 7. AI-agent instructions for Phase 4.0

**Before writing code:**

1. Read every URL in §6 for the layer you're working on.
2. Read `docs/references/library-lookup-protocol.md`.
3. Read `docs/references/0007-keychain-only-secrets.md` — IMAP/SMTP/NNTP passwords go in keychain.
4. Read Phase 3 §3.7 (editor) — compose dialog reuses it.

**While writing code:**

1. **No private keys in process memory.** All PGP operations via GnuPG subprocess.
2. **Spam training is HMAC-protected.** Don't allow training without a valid token.
3. **Body fetch is lazy.** List view shows headers only; body fetched on open.
4. **NNTP binary downloads respect cancellation.** User can cancel per-file or per-batch.
5. **PAR2 repair is automatic but documented.** If repair fails, don't silently delete files.

**After writing code:**

1. Run `cargo test -p hypernext-correspondence`.
2. Update `worklog.md`.
3. Conventional Commits: `feat(4.0): add IMAP client`, `test(4.0): cover PGP verify flow`.
